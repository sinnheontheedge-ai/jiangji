【总目标】
在不重写核心算法前提下，把现有系统“切干净”，交付一个最轻便、最稳定、可长期实盘运行的单人交易系统版本。
必须保留我的全部核心需求，彻底移除 Web 平台化累赘、死代码、未使用模块、无效集成。

【绝对禁止】
- 禁止 Web UI / 前后端分离 / 浏览器端界面
- 禁止 REST API 作为交易主链路（允许仅用于本地 GUI 调参的本机 IPC/本机HTTP，但不得进入交易核心链路）
- 禁止 UI WebSocket / 内部 WebSocket 推送体系（仅允许交易所 WebSocket）
- 禁止 EventBus（交易核心链路禁止依赖 publish/subscribe）
- 禁止 Plugin Loader / 插件系统（禁止动态插件注册、插件生命周期）

- 禁止轮询触发交易逻辑（见 ON TICK 约束）
- 禁止为了“架构漂亮”增加抽象层

事件来源必须仅为：
1) Binance Market WebSocket（行情 tick/mark price等）
2) Binance User Data Stream（订单成交/余额/仓位变动）

禁止：
- 定时轮询交易所 REST 来做交易决策/风控/资金动作
- 定时轮询数据库来做交易决策/风控/资金动作
（配置热加载可以低频检查文件变化，但不得驱动交易逻辑）

================================================
五、策略 Warmup：自适应预热（Adaptive Warmup）+ 就绪门禁（Readiness Gate）
================================================
硬性要求：
1) 禁止固定历史根数（例如固定500）作为 Warmup 标准。
2) 禁止要求每个策略声明固定历史长度。
3) Warmup 未 READY 前，禁止产生任何交易信号与下单。

实现必须采用：
Adaptive Warmup + Readiness Gate + On-demand Backfill（自适应预热 + 就绪门禁 + 按需回补）

规则：
A) 按需回补（On-demand Backfill）
- 优先读取本地缓存历史K线；不足再从交易所回补
- 回补窗口逐步扩展（例如 200→500→1000→2000…，或依据“计算失败原因”扩展），直到 READY

B) 就绪判定（Readiness Gate）
- READY 必须基于策略运行时真实计算结果，而不是预设长度
- 若任一指标/条件计算出现：数据不足/窗口不够/NaN/缺失，则 NOT READY，并继续回补
- 只有当该监控项所需全部指标与条件均可计算且无 NaN/缺失窗口，才判定 READY

C) 多周期/多监控项
- 对每个 (symbol, timeframe, strategy) 监控项分别判定 READY
- 未 READY 的监控项不得交易，但不得影响其他已 READY 的监控项

D) READY 后启动检查（Startup Signal Check）
- 某监控项首次 READY 后，必须立即做一次“启动时刻条件检查”
- 是否允许 READY 后立即进场必须可配置（默认：允许产生信号，但仍需通过风控/资金门禁）

E) 防死循环保护
- 必须设定最大回补上限（到交易所允许范围）
- 若到上限仍 NOT READY：禁止该监控项交易，并输出明确错误（指出哪个指标/条件导致 NOT READY）

================================================
六、风控（TP/SL/Step Lock）最终口径（必须严格按此实现）
================================================
Step Lock 数学公式（严格基于 entry_price；X/M为触发阈值，Y/N为锁定利润止损）：

LONG
触发：current_price >= entry_price * (1 + profit_threshold/100)
新SL：new_sl = entry_price * (1 + stop_loss_percent/100)

SHORT
触发：current_price <= entry_price * (1 - profit_threshold/100)
新SL：new_sl = entry_price * (1 - stop_loss_percent/100)

要求：
- profit_threshold 与 stop_loss_percent 都是用户可配置
- 强制校验 profit_threshold > stop_loss_percent
- 必须 tick 级触发（ON TICK），禁止K线级才触发
- 档位/状态必须持久化，重启必须恢复
- 禁止跳级、重复触发、错向触发
- UI/界面概念必须是“按进场方向波动%”，不是“涨幅%”

================================================
七、订单保护单管理（必须做到，否则视为不可实盘）
================================================
A) Step Lock 触发后的“撤旧挂新”（强制）
当 Step Lock 触发并需要更新 SL 时，必须原子化执行：
1) 计算新 SL
2) 撤销旧 SL 挂单
3) 挂出新 SL
4) 更新本地与数据库状态
要求：
- 任意时刻同一仓位只允许存在 1 个 SL 挂单
- 新 SL 挂出失败必须有补偿策略（不得默默失控）

B) TP/SL 成交后的清理（强制）
当 TP 或 SL 任意一个成交导致仓位为 0：
必须立即（基于 User Data WS 成交回报）撤销剩余所有挂单：
- 剩余 TP
- 剩余 SL
- 其他保护单
禁止平仓后仍存在挂单（防反向开仓风险）

================================================
八、执行安全（任何资金风险都视为P0）
================================================
必须满足：
- 所有平仓单 reduceOnly=True（强制，不允许缺失）
- 幂等：所有下单必须使用 clientOrderId，并且必须有防重放机制（网络重试不得导致重复下单）
- 持仓方向校验
- 最小下单精度/步进校验（按交易所 filters 截断）
- 部分成交正确处理
- “下单成功但 DB 写入失败”必须补偿（撤单/对账修正），禁止悄悄失控
- 单仓模式必须硬拦截：账户级同一时刻只允许存在 1 笔未平仓仓位（不区分交易对/方向）

================================================
九、资金管理（核心中的核心，必须 WS 驱动）
================================================
资金管理必须完全基于 WebSocket 事件触发（User Data Stream），禁止轮询余额实现。

必须保留并严格实现以下已定稿规则：
1) 杠杆降级：L_actual = min(L_group, L_symbol_max)
2) 维持名义仓位：
   若杠杆降级，为保持名义仓位一致：
   M_target = M_plan * (L_group / L_actual)
3) 下单前保证金不足：
   先从现货→合约自动划转差额 Δ=max(0, M_target - M_avail)
   划转失败或补足后仍不足 → 放弃该次下单并通知（账户隔离）
4) 盈利提取（强制）：
   触发时机：每次平仓结算完成后 + 每次下单前
   循环执行直到合约账户余额回到固定初始保证金 Y
   划转方向：合约→现货
5) 金额精度：
   所有资金/金额计算必须 Decimal
   最终下单金额按交易所 filters 截断（禁止四舍五入导致不合法）
6) 账户隔离通知与配置：严禁跨账户推送（即使当前单人也必须保留隔离逻辑，避免未来扩展污染）
